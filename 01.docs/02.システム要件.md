# 1. 本書の目的

本書は、要件定義書に記載されたゲーム仕様を、Webアプリケーションとして実現するためのシステム要件に整理したものである。画面、ゲームエンジン、データ、状態遷移、品質および運用上の要件を定める。

対戦方式、デプロイ環境、およびゲームルールの一部は未確定である。これらに依存する要件は暫定または未確定として扱い、確定前に最終仕様とみなしてはならない。

# 2. システム概要

## 2.1 システムの目的

ブラウザ上でドロー大富豪を開始し、設定されたルールに従ってプレイし、ゲーム結果を表示できるシステムを提供する。初期開発ではゲームルールの正確な処理と操作性を優先する。

## 2.2 システム境界

| 区分 | 対象 |
|---|---|
| システムに含む | ゲーム設定、カード生成・配布、手札・山札管理、合法手判定、ターン進行、特殊効果処理、勝敗・順位判定、ゲーム画面・結果画面 |
| 将来対応 | CPU対戦、オンライン対戦、戦績保存、ランキング |
| 対象外または未確定 | サーバー構成、認証、永続化方式、対戦方式、デプロイ先、対応ブラウザの具体的なバージョン |

## 2.3 利用者と利用環境

- 利用者はWebブラウザからゲームを操作する。
- PCおよびスマートフォンで基本的なゲーム操作ができること。
- 参加人数は2～5人を想定する（最終確認が必要）。
- 同一端末でのローカル対戦、CPU対戦、オンライン対戦のいずれを初期提供するかは未確定である。

# 3. システム構成要件

## 3.1 論理構成

システムは、少なくとも次の責務を分離して構成する。実装技術および配置形態は本書では指定しない。

| 構成要素 | 責務 |
|---|---|
| UI | 設定入力、手札や場の表示、カード選択、操作結果・ゲーム状態の提示 |
| ゲームエンジン | 操作の検証、ルール判定、状態遷移、ゲーム結果の決定 |
| 山札管理 | カード生成、シャッフル、配布、回収および再利用 |
| ルール処理 | 役の判定、強弱比較、縛り、革命、11バック、各特殊効果の判定 |
| 効果処理 | 7渡し、10捨て、5スキップ等、プレイヤー選択を伴う効果の進行 |
| ゲーム状態管理 | プレイヤー、手札、山札、場、進行フェーズ、効果待ち状態および結果の整合性維持 |

ゲームエンジンはUIフレームワークに依存させず、将来サーバー上で実行する構成へ移行できるようにする。すべてのゲーム操作はゲームエンジンを経由させる。

## 3.2 処理構成

- UIは操作要求をゲームエンジンに渡し、判定済みの状態またはエラーを受け取る。
- ゲームエンジンは、合法性を検証する前にゲーム状態を変更してはならない。
- 状態更新は一貫性を保ち、カードIDの重複やカードの所在不明を検出できること。
- 特殊効果で利用者の選択が必要な場合、選択完了まで処理中の効果と進行フェーズを保持する。
- 状態およびゲーム結果は、画面表示とゲームロジックで別々の判定を持たず、ゲームエンジンの判定を正とする。

## 3.3 実行・配置環境

- 初期提供形態はWebブラウザとする。
- PCおよびスマートフォン向けのレスポンシブUIを提供する。
- クライアントのみで実行するか、サーバーを含む構成とするかは対戦方式決定後に確定する。
- デプロイ先、サーバー、データベース、対応ブラウザおよび通信方式の詳細は未確定とする。

# 5. ゲーム状態・データ要件

## 5.1 管理するデータ

システムは、少なくとも以下の情報を管理する。具体的な型・永続化方法は実装設計で定める。

| データ | 管理内容 |
|---|---|
| Card | 一意なカードID、スート、ランク、ジョーカー判定 |
| Player | プレイヤーID、表示名、手札、順序、上がり状態、順位 |
| GameState | ゲームID、プレイヤー、山札、現在のプレイヤー、場、革命、11バック、縛り、進行フェーズ、ターン番号、処理待ち効果、結果 |
| Trick | 役種別、枚数、ジョーカー補完後の数字・スート、比較用強度、出したプレイヤー、革命成立、ジョーカー1枚出しかどうか |

場の論理状態は、場に出た物理カードの所在とは独立して保持する。カード回収後も次の判定に必要な役、数字、スート、枚数、階段、縛り、直前のプレイヤーおよび状態フラグを失わないこと。

## 5.2 データ整合性

- 1ゲーム内のカードIDは一意であること。
- 各カードは、山札・各プレイヤーの手札・その他定義された保有領域のいずれかで整合して管理されること。
- 1枚のカードが複数の領域に重複して存在しないこと。
- カードの提出、ドロー、譲渡、破棄、回収の各処理後にカード枚数とIDの整合性を検査できること。
- 不正なカードID、現在の手番外の操作、存在しない対象カードを受け付けないこと。
- ゲーム状態はシリアライズ可能な形式で管理できること。

## 5.3 進行フェーズ

ゲームエンジンは、少なくとも次の状態を区別して処理する。

| 状態 | 意味 |
|---|---|
| WAITING | ゲーム開始待ち |
| DEALING | カード配布中 |
| PLAYING | 通常プレイ中 |
| DRAWING | 強制ドロー中 |
| EFFECT_RESOLUTION | 特殊効果の処理中 |
| TURN_END | ターン終了処理中 |
| TRICK_RESET | 場のリセット中 |
| FINISHED | ゲーム終了 |

有効な操作は現在の状態に応じて制御し、効果選択中や配布中などに不適切な操作を受け付けないこと。

## 5.4 1ターンの処理

確定したルールに応じ、ゲームエンジンは原則として次の処理を行う。

1. 現在のプレイヤーおよび進行状態を確認する。
2. カード提出またはパス操作を検証する。
3. パスの場合はドロー処理を行う。山札枯渇時は確定した規則に従う。
4. ドロー後のカード提出があれば、手札全体を対象に合法性を検証する。
5. 特殊効果を適用し、利用者の選択が必要な場合は処理待ち状態にする。
6. 効果解決後に上がり条件を判定する。
7. 使用済みカードを定められたタイミングで回収する。
8. 効果および場の状態に従って次のプレイヤーまたは次の場を決定する。

全員パス時の場のリセット条件、強制ドロー後のターン終了条件、効果間の優先順位は、未確定事項の決定後に確定する。

# 6. 外部インターフェース要件

## 6.1 利用者インターフェース

- PCとスマートフォンでカード選択および主要操作を実行できること。
- 操作可能なプレイヤー、選択中カード、場の状態、効果処理待ちを区別して表示すること。
- 不正または現在実行できない操作をゲーム状態に反映しないこと。
- 推奨機能として合法手の強調表示、手札の並び替え、操作履歴を提供できる構成とする。

## 6.2 通信インターフェース

- オンライン対戦を実装する場合はHTTPSを使用する。
- クライアントから送信されたカードIDおよび操作内容は、サーバー側で再検証する。
- オンライン対戦時はゲーム状態の競合および同一操作の重複実行を防止する。
- 通信プロトコル、認証、再接続、タイムアウト、サーバー権限の詳細はオンライン対戦方式決定後に定める。

# 7. 非機能要件

## 7.1 性能・応答性

- カード選択および合法手判定を、プレイの妨げにならない応答性で実行すること。
- ターン更新時に画面全体を不要に再読み込みしないこと。
- 複数の特殊効果が組み合わさる場合でも処理が停止しないこと。
- 具体的な応答時間、同時接続数等の数値目標は未定義であり、対戦方式と提供規模を決定した後に設定する。

## 7.2 セキュリティ・公平性

- ゲーム状態を変更するすべての操作をゲームエンジンで検証すること。
- UI操作のみで不正なゲーム状態を成立させないこと。
- 他プレイヤーの非公開手札を不正に参照できないこと。
- クライアントから受け取るカードID、プレイヤーIDおよび操作対象を検証すること。
- オンライン対戦では、カード配布、合法手、勝敗をサーバー側で検証すること。
- オンライン通信を行う場合はHTTPSを使用すること。

## 7.3 保守性・拡張性

- ゲームロジックとUIを分離すること。
- 特殊効果を個別に追加・変更できる構成とすること。
- カード強弱判定を共通化すること。
- ゲーム状態をシリアライズ可能にし、ブラウザ実行からサーバー実行へ移行可能な設計とすること。
- ルール判定、状態遷移、特殊効果および不正操作を自動テストで検証できること。
- 将来の対戦方式、戦績保存およびランキングの追加を妨げないこと。

## 7.4 可用性・障害時の扱い

- 山札枯渇やドロー不能によってゲーム処理が停止しないこと。
- ゲーム状態の不整合を検出できること。
- エラー時に成功したように見える状態遷移を行わないこと。
- セッション復旧、ゲーム中断後の再開、障害監視および稼働率の要件は、配置・対戦方式決定後に定める。

## 7.5 互換性・アクセシビリティ

- PC・スマートフォンで主要なゲーム操作ができるレスポンシブUIとする。
- 対応ブラウザ、画面サイズの範囲、アクセシビリティ基準の具体値は未確定とし、提供対象決定後に定める。

# 8. テスト・受入要件

## 8.1 テスト要件

- カード強弱、革命、11バック、役判定、縛り、特殊効果、上がり判定のユニットテストを作成する。
- ゲーム開始から終了までの状態遷移とターン処理を統合テストで検証する。
- 不正なカードID、手番外操作、合法でない組み合わせを拒否することをテストする。
- ドロー後の手札全体からのカード選択、山札枯渇、カード回収、効果選択中の状態をテストする。
- 重要な組合せテストとして、要件定義書のTC-001～TC-020を実装可能な形にし、確定したルールに基づいて期待結果を固定する。
- 未確定ルールに依存するテストは、そのルール確定後に受入条件として確定する。

## 8.2 MVP受入条件

次の条件を満たしたとき、MVP完成とする。

- 確定済みのゲームルールが実装されている。
- 手札・山札・場におけるカードIDと所在が整合している。
- 強制ドロー後も合法な操作を行える。
- 特殊効果が確定した優先順位で解決される。
- 革命と11バックの強弱変更が正しく動作する。
- 上がり禁止ルールが確定仕様に沿って適用される。
- ゲームを開始から終了までプレイでき、結果と順位を表示できる。
- PCおよびスマートフォンで基本操作ができる。
- 重要なゲームロジックの自動テストが存在し、重大な進行停止不具合がない。
