# ドロー大富豪 PoC 社内サーバー デプロイ手順書

**対象：** `02.poc`（Draw Daifugo PoC）  
**想定読者：** 社内サーバーへ配置・運用する担当者  
**ステータス：** PoC用（検証環境向け）

---

# 1. 概要

PoC は Node.js の小さなサーバー1つで動作します。サーバーは次の2つを担当します。

- 画面（ビルド済みの HTML / JS / CSS）の配信
- **オンライン対戦**の進行（WebSocket）。ルームの管理、カード配布、合法手・勝敗の判定をサーバー側で行い、各プレイヤーには自分の手札だけを送ります。

「この端末で遊ぶ」（1台を回して遊ぶローカル対戦）はブラウザ内だけで動き、サーバーとは通信しません。

```text
利用者のブラウザ ──HTTP / WebSocket(/ws)──▶ 社内サーバー :8090 ──▶ Dockerコンテナ（Node.js）
                       （任意）前段のリバースプロキシで TLS・アクセス制御
```

| 項目 | 内容 |
|---|---|
| 配信方式 | Docker イメージ（node:26-alpine）1コンテナ |
| コンテナのポート | 8090/tcp（HTTP と WebSocket を同じポートで提供） |
| エンドポイント | `/`（画面）、`/ws`（オンライン対戦）、`/healthz`（ヘルスチェック） |
| 永続データ | なし（DB・ボリューム・バックアップ不要） |
| 対戦中のデータ | **サーバーのメモリ上のみ**。コンテナを再起動・更新すると、進行中のオンライン対戦とルームはすべて消える |
| 構成の制約 | **1コンテナでのみ運用する**（ルームがメモリ上にあるため、複数台への負荷分散はできない） |
| 外部通信 | なし（実行時にサーバーから外部へ通信しない） |
| ヘルスチェック | イメージに組み込み済み（30秒ごとに `http://127.0.0.1:8090/healthz` を確認） |
| 実行ユーザー | コンテナ内の一般ユーザー `node`（root では動かない） |
| 認証・アクセス制御 | **なし**（「6. 公開範囲とアクセス制御」を必ず確認すること） |

サーバー側の主な制限値（`server/rooms.ts`）：

| 項目 | 値 |
|---|---|
| 同時に存在できるルーム数 | 200 |
| 1ルームの人数 | 2～5人 |
| 切断したプレイヤーの手番 | 45秒後に自動でパス（7渡し・10捨ては自動選択） |
| 全員が切断したルーム | 15分後に削除 |
| 1接続あたりの受信 | 1秒に20件まで、1件8KBまで |

> 更新時はコンテナの入れ替えで数秒程度アクセスできなくなり、**進行中のオンライン対戦は終了します**。利用者が少ない時間帯に実施し、事前に告知してください。ローカル対戦はブラウザのメモリ上にあるため、利用者が再読み込みしない限り中断されません。

# 2. 前提条件

## 2.1 社内サーバー

- Linux（x86_64）
- Docker Engine 20.10 以上（`docker version` で確認）
- デプロイ担当者が `docker` コマンドを実行できること（root または `docker` グループ）
- 公開ポート（既定：8090）が他のサービスと重複していないこと

```bash
docker version
sudo ss -ltnp | grep ':8090' || echo "8090 は空いています"
```

> サーバーが ARM（aarch64）の場合は、ビルド時に `--platform linux/arm64` を指定するか、サーバー上でビルドしてください（手順A）。

## 2.2 ネットワーク要件

ビルドを行うマシンのみ、次へのアクセスが必要です。実行時には不要です。

| 接続先 | 用途 |
|---|---|
| Docker Hub（registry-1.docker.io 等） | ベースイメージ `node:26-alpine` の取得 |
| npm レジストリ（registry.npmjs.org） | 依存パッケージの取得（`npm ci`） |
| GitHub（github.com/LS-Dev-JP/daifugo） | ソースの取得（手順Aのみ） |

社内サーバーからこれらに接続できない場合は **手順B（オフライン配置）** を使用します。

## 2.3 デプロイ対象

- `main` ブランチに push 済みのコミットをデプロイします。未コミットの変更を含めないでください。
- イメージのタグには日付とコミットハッシュを使い、どのソースを配置したか追跡できるようにします（例：`20261108-a1b2c3d`）。

# 3. 事前確認（開発端末）

デプロイ前に、テストとビルドが通ることを確認します。

```powershell
Set-Location .\02.poc
npm ci
npm test
npm run build
```

すべて成功したら、変更を `main` に push しておきます。

# 4. イメージの作成と配置

サーバーの環境に応じて、手順A または 手順B のどちらかを実施します。

| 条件 | 手順 |
|---|---|
| サーバーから GitHub・Docker Hub・npm に接続できる | **手順A：サーバー上でビルド** |
| サーバーが外部に接続できない／ビルドを持ち込みたくない | **手順B：開発端末でビルドして持ち込み** |

## 4.1 手順A：サーバー上でビルド

### A-1. ソースの取得

初回：

```bash
sudo mkdir -p /opt/draw-daifugo
sudo chown "$USER" /opt/draw-daifugo
git clone https://github.com/LS-Dev-JP/daifugo.git /opt/draw-daifugo/src
```

2回目以降：

```bash
cd /opt/draw-daifugo/src
git fetch origin
git checkout main
git pull --ff-only origin main
```

> リポジトリが非公開の場合は、デプロイ用の読み取り専用トークンまたはデプロイキーを使用してください。個人のアカウント情報をサーバーに保存しないでください。

### A-2. イメージのビルド

```bash
cd /opt/draw-daifugo/src
TAG="$(date +%Y%m%d)-$(git rev-parse --short HEAD)"
docker build -t "draw-daifugo-poc:${TAG}" ./02.poc
docker tag "draw-daifugo-poc:${TAG}" draw-daifugo-poc:latest
echo "ビルドしたタグ: ${TAG}"
```

ビルドの中で `npm ci`、型チェック、画面とサーバーの本番ビルドが実行されます。失敗した場合はイメージが作成されないため、稼働中のコンテナには影響しません。

→ 「5. コンテナの起動」へ進みます。

## 4.2 手順B：開発端末でビルドして持ち込み

### B-1. 開発端末でビルド・書き出し（Windows / PowerShell）

リポジトリのルートで実行します。

```powershell
$TAG = "$(Get-Date -Format yyyyMMdd)-$(git rev-parse --short HEAD)"
docker build --platform linux/amd64 -t "draw-daifugo-poc:$TAG" .\02.poc
docker save "draw-daifugo-poc:$TAG" -o ".\draw-daifugo-poc_$TAG.tar"
Get-FileHash ".\draw-daifugo-poc_$TAG.tar" -Algorithm SHA256
```

表示された SHA256 ハッシュを控えておきます。

### B-2. サーバーへ転送

```powershell
scp ".\draw-daifugo-poc_$TAG.tar" <ユーザー>@<サーバー>:/tmp/
```

（scp が使えない場合は、社内のファイル共有など承認済みの手段で転送してください。）

### B-3. サーバーで読み込み

```bash
TAG=<B-1で作成したタグ>
sha256sum "/tmp/draw-daifugo-poc_${TAG}.tar"   # B-1 のハッシュと一致すること
docker load -i "/tmp/draw-daifugo-poc_${TAG}.tar"
docker tag "draw-daifugo-poc:${TAG}" draw-daifugo-poc:latest
rm "/tmp/draw-daifugo-poc_${TAG}.tar"
```

→ 「5. コンテナの起動」へ進みます。

# 5. コンテナの起動

## 5.1 初回起動

```bash
HOST_PORT=8090   # 社内で公開するポート。重複する場合は変更する
docker run -d \
  --name draw-daifugo \
  --restart unless-stopped \
  -p "${HOST_PORT}:8090" \
  --read-only --tmpfs /tmp \
  --memory 256m \
  --log-opt max-size=10m --log-opt max-file=3 \
  "draw-daifugo-poc:${TAG}"
```

| オプション | 目的 |
|---|---|
| `--restart unless-stopped` | サーバー再起動や異常終了時に自動で再起動する |
| `-p ${HOST_PORT}:8090` | ホストのポートをコンテナの 8090 に割り当てる |
| `--read-only` / `--tmpfs /tmp` | コンテナ内のファイル改ざんを防ぐ（一時領域のみ書き込み可） |
| `--memory 256m` | メモリ使用量の上限（通常の利用では数十MB程度） |
| `--log-opt ...` | コンテナのログが増え続けないようにする |

> 前段にリバースプロキシを置き、同じサーバー内からのみ接続させる場合は `-p "127.0.0.1:${HOST_PORT}:8090"` とし、外部から直接アクセスできないようにします。

## 5.2 動作確認

```bash
docker ps --filter name=draw-daifugo                               # STATUS が Up であること
sleep 10
docker inspect --format '{{.State.Health.Status}}' draw-daifugo    # healthy であること
curl -s "http://localhost:${HOST_PORT}/healthz"; echo                 # ok と表示されること
curl -s -o /dev/null -w '%{http_code}\n' "http://localhost:${HOST_PORT}/"   # 200 であること
docker logs --tail 20 draw-daifugo                                 # 「Draw Daifugo server listening on :8090」と出ていること
```

続いて、社内の別の端末のブラウザから `http://<サーバー>:<HOST_PORT>/` を開き、次を確認します。

| # | 確認内容 | 期待結果 |
|---|---|---|
| 1 | トップ画面を開く | 「Draw 大富豪」の設定画面が表示される |
| 2 | 2人・5枚で「ゲームを始める」 | 受け渡し画面が表示され、「手札を表示する」で手札が出る |
| 3 | カードを1枚選ぶ | 「出せます」または出せない理由が表示される |
| 4 | パスする | 手札が1枚増え、`NEW` 表示が付く |
| 5 | スマートフォンで開く | 横スクロールせずに操作できる |
| 6 | 「オンライン対戦」で名前を入れ、募集人数「2人」で「2人で募集を始める」 | 4桁のルーム番号が表示される |
| 7 | 別の端末（またはシークレットウィンドウ）で「オンライン対戦」を開く | 「募集中のルーム」に手順6のルーム番号が表示される |
| 8 | 一覧の「参加」を押す | 両方の画面に「メンバーがそろいました」と5秒のカウントダウンが表示され、自動でゲームが始まる |
| 8a | 手番の人がカードを出す | もう一方の画面に場のカードが反映される。相手の手札は枚数だけが表示される |
| 9 | 参加者側でブラウザを再読み込み | 同じ席・同じ手札のままゲームに戻る |
| 10 | ブラウザの開発者ツール → Console | エラーが出ていない |

# 6. 公開範囲とアクセス制御

この PoC には **認証機能がありません**。URL を知っている人は誰でもアクセスできます。社内ネットワークへ公開する際は、少なくとも次のいずれかを行ってください。

1. **ファイアウォールで接続元を限定する**（推奨・最低限）

   ```bash
   # firewalld の例：検証メンバーのセグメントからのみ許可
   sudo firewall-cmd --permanent --new-zone=daifugo
   sudo firewall-cmd --permanent --zone=daifugo --add-source=<許可するセグメント 例: 10.0.10.0/24>
   sudo firewall-cmd --permanent --zone=daifugo --add-port=8090/tcp
   sudo firewall-cmd --reload
   ```

   > Docker が公開したポートは iptables のルールにより firewalld / ufw の設定を通らない場合があります。設定後、許可していない端末から接続できないことを必ず確認してください。確実に制限するには、5.1 の注記のように `127.0.0.1` にのみ公開し、前段のリバースプロキシで制御します。

2. **社内のリバースプロキシを前段に置く**（TLS・認証が必要な場合）

   既存のリバースプロキシ（nginx 等）から `http://127.0.0.1:8090/` へ転送します。オンライン対戦は WebSocket を使うため、**`/ws` の Upgrade ヘッダーの転送と、長めの読み取りタイムアウトが必須**です。これがないと「サーバーに接続しています…」のまま進みません。nginx の場合の設定例：

   ```nginx
   server {
       listen 443 ssl;
       server_name daifugo.<社内ドメイン>;

       ssl_certificate     /etc/nginx/certs/<証明書>.crt;
       ssl_certificate_key /etc/nginx/certs/<秘密鍵>.key;

       # 必要に応じて Basic 認証または社内 SSO を設定
       auth_basic           "Draw Daifugo PoC";
       auth_basic_user_file /etc/nginx/.htpasswd-daifugo;

       location / {
           proxy_pass http://127.0.0.1:8090;
           proxy_http_version 1.1;
           proxy_set_header Upgrade $http_upgrade;
           proxy_set_header Connection $connection_upgrade;
           proxy_set_header Host $host;
           proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
           proxy_set_header X-Forwarded-Proto $scheme;
           proxy_read_timeout 1h;   # 対戦中の WebSocket が切断されないようにする
       }
   }

   # http ブロックに1回だけ定義する
   map $http_upgrade $connection_upgrade {
       default upgrade;
       ''      close;
   }
   ```

   アプリはパスを相対参照（`base: "./"`）でビルドしているため、`https://<ホスト>/daifugo/` のようなサブパス配下に置くこともできます。その場合は `location /daifugo/ { proxy_pass http://127.0.0.1:8090/; ... }` とし（末尾の `/` が必要）、上と同じ WebSocket 用の設定を入れます。

   > Basic 認証を使う場合、ブラウザは WebSocket 接続にも同じ認証情報を自動で付けるため、追加の設定は不要です。

# 7. 更新手順

1. 「3. 事前確認」を実施し、更新内容を `main` に push する。
2. 新しいイメージを作成する（手順A の A-1〜A-2、または手順B）。
3. **進行中のオンライン対戦が終了することを利用者に告知する**（入れ替えるとルームはすべて消える）。
4. 稼働中のタグを控えてから、コンテナを入れ替える。

```bash
# 現在のタグを控える（ロールバック用）
PREV_IMAGE="$(docker inspect --format '{{.Config.Image}}' draw-daifugo)"
echo "${PREV_IMAGE}"

# 入れ替え（数秒停止）
docker stop draw-daifugo
docker rm draw-daifugo
docker run -d \
  --name draw-daifugo \
  --restart unless-stopped \
  -p "${HOST_PORT}:8090" \
  --read-only --tmpfs /tmp \
  --memory 256m \
  --log-opt max-size=10m --log-opt max-file=3 \
  "draw-daifugo-poc:${TAG}"
```

5. 「5.2 動作確認」を実施する。
6. 利用者に、ブラウザの再読み込みで新しい版が反映されることを案内する（JS / CSS はファイル名にハッシュが付くため、キャッシュの削除は不要）。オンライン対戦中だった利用者の画面は、トップ画面に戻ります。

# 8. ロールバック

更新後に問題が見つかった場合は、控えておいた前のイメージで起動し直します。

```bash
docker images draw-daifugo-poc          # 残っているタグを確認
docker stop draw-daifugo && docker rm draw-daifugo
docker run -d \
  --name draw-daifugo \
  --restart unless-stopped \
  -p "${HOST_PORT}:8090" \
  --read-only --tmpfs /tmp \
  --memory 256m \
  --log-opt max-size=10m --log-opt max-file=3 \
  "${PREV_IMAGE}"
```

ロールバックできるよう、**直近2〜3世代のイメージは削除せずに残してください**。それより古いものは次のコマンドで削除できます。

```bash
docker rmi draw-daifugo-poc:<不要になったタグ>
docker image prune -f      # タグのない中間イメージを削除
```

# 9. 停止・撤去

```bash
docker stop draw-daifugo                        # 一時停止（再開は docker start draw-daifugo）
docker rm draw-daifugo                          # コンテナ削除
docker rmi $(docker images -q draw-daifugo-poc) # イメージ削除

```

「6. 公開範囲とアクセス制御」で追加したファイアウォール・リバースプロキシの設定も削除します。

# 10. トラブルシューティング

| 症状 | 確認・対処 |
|---|---|
| `docker build` が `npm ci` で失敗する | npm レジストリに接続できるか確認する。プロキシ環境では `docker build --build-arg HTTP_PROXY=... --build-arg HTTPS_PROXY=...` を指定する。接続できない場合は手順B を使う |
| `docker build` が型エラー・テスト対象のエラーで失敗する | 開発端末で `npm run build` が通るか確認する（「3. 事前確認」） |
| ベースイメージが取得できない | Docker Hub への接続、または社内ミラーの設定（`/etc/docker/daemon.json` の `registry-mirrors`）を確認する |
| `docker run` で `port is already allocated` | `HOST_PORT` を変更するか、ポートを使っているプロセスを確認する（`sudo ss -ltnp \| grep :8090`） |
| ヘルスチェックが `unhealthy` | `docker logs draw-daifugo` でエラーを確認する。`dist/index.html not found` の場合はビルドが不完全なため、イメージを作り直す |
| オンライン対戦で「サーバーに接続しています…」から進まない | リバースプロキシで WebSocket（`Upgrade` / `Connection` ヘッダー）を転送しているか確認する（「6. 公開範囲とアクセス制御」）。ブラウザの開発者ツール → Network → WS で `/ws` の接続状況を確認する |
| 対戦中に「再接続しています…」が頻繁に出る | リバースプロキシの読み取りタイムアウト（`proxy_read_timeout`）が短すぎないか確認する。サーバーは30秒ごとに死活確認を送っている |
| 「ルームが終了したか、参加情報が見つかりません」と出る | コンテナの再起動・更新でルームが消えたか、全員が15分以上切断してルームが削除された。ルームを作り直す |
| 「ルーム数が上限に達しています」と出る | 同時ルーム数の上限（200）に達している。放置されたルームは全員切断から15分で自動削除される |
| サーバー上では `curl` で 200 だが、他の端末から開けない | ファイアウォール・セキュリティグループで `HOST_PORT` が許可されているか、`127.0.0.1` にのみ公開していないか確認する |
| 画面が真っ白になる | ブラウザの開発者ツールで JS の読み込みエラーを確認する。サブパス配下に置いた場合は `proxy_pass` 末尾の `/` を確認する |
| 古い画面が表示される | ブラウザを再読み込みする。解消しない場合は `docker ps` で新しいタグのコンテナが動いているか確認する |
| `exec format error` で起動しない | サーバーと異なる CPU アーキテクチャでビルドしている。`--platform` を指定してビルドし直す |

# 11. 運用メモ

- **ログ：** `docker logs draw-daifugo`。起動・停止とサーバーエラーのみを出力し、アクセスログは出さない。アクセス記録が必要な場合は前段のリバースプロキシで取得する。
- **バックアップ：** 永続データがないため不要。ソースは Git、イメージはタグで再作成できる。
- **ベースイメージの更新：** `node:26-alpine` のセキュリティ更新を取り込むには、ソースに変更がなくても定期的に再ビルドして入れ替える（`docker build --pull ...`）。入れ替え時は進行中のオンライン対戦が終了する点に注意する。
- **個人情報：** オンライン対戦で入力された表示名と手札は、対戦中のみサーバーのメモリに置かれ、ディスクには保存されない。ローカル対戦の内容はサーバーへ送信されない。
- **PoC の範囲外：** 認証、戦績保存、ルームの永続化（再起動後の復元）、複数台構成は未実装です。本番運用の前に、要件定義書の未確定事項（Q-01、ENV-01、ENV-02）を確定してください。
